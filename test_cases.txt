================================================================================
PARTSELECT PARTS ASSISTANT — TEST CASES
================================================================================

Test cases derived from the case-study requirements and the features we built.
Every part number and model number below is a REAL entry in the seed catalog, so
each expected result is concrete and checkable.

--------------------------------------------------------------------------------
HOW TO EXECUTE TESTS (read this first)
--------------------------------------------------------------------------------

There are two kinds of test below:

  [UI]  -> Run in the browser. Open http://localhost:3000, type the input into
           the chat box, press Send, and check the result against "EXPECT".

  [API] -> Run from a terminal with curl (no browser). Copy the command, run it,
           and check the JSON output against "EXPECT". These prove the backend
           behavior directly.

Before testing, make sure BOTH servers are running:

  Backend:   cd backend && source venv/bin/activate
             uvicorn app.main:app --reload --port 8000
  Frontend:  npm start         (from the repo root; opens localhost:3000)

Quick health check:
  curl -s http://localhost:8000/health
  EXPECT: {"status":"ok"}

The generic curl command shape used by all [API] tests:

  curl -s -X POST http://localhost:8000/chat \
    -H "Content-Type: application/json" \
    -d '{"messages":[{"role":"user","content":"YOUR MESSAGE HERE"}]}'

The response JSON has these fields:
  content      -> the assistant's text answer (markdown)
  tool_calls   -> list of {tool, input, result} the agent used
  suggestions  -> list of follow-up chip strings

Tip: pipe through "| python3 -m json.tool" to read it formatted, or
"| python3 -c 'import sys,json; d=json.load(sys.stdin); print(d[\"content\"])'"
to print just the answer.

NOTE ON VARIABILITY: this is an LLM agent, so exact wording varies between runs,
and for ambiguous symptoms it may lead with a clarifying question on one run and a
part on another. The PASS conditions below are written to allow that — they check
the behavior (right tool, right part, declines out-of-scope, gives DIY checks),
not an exact string. The same logic is automated in /tmp/ps-verify/run_all.py,
which runs the API cases and prints PASS/FAIL (21/21 expected).

SECTION C — TROUBLESHOOTING / SYMPTOM DIAGNOSIS
================================================================================

The assistant is a REPAIR assistant, not just a parts catalog. A good
troubleshooting answer does more than list parts to buy. Expect it to:
  (a) ask a clarifying question when the symptom is ambiguous,
  (b) give FREE non-part checks first (clean filter, check hose, settings, etc.),
  (c) surface the likely part(s) via the troubleshoot tool, with WHY each one
      could be the cause and how to tell,
  (d) offer support only as a LAST RESORT ("if those checks don't fix it").
Because the model decides per-message, a given symptom may lead with parts OR
with clarifying questions — both are valid. The cases below check for that
richer behavior, not just a part number.

--- C1: Dishwasher not draining ------------------------------------------------
TYPE: [UI] and [API]
INPUT:  My dishwasher won't drain, there's standing water
EXPECT: FREE checks first (clean filter/strainer, check drain hose for kinks,
        garbage disposal knockout plug, air gap), AND the troubleshoot tool
        surfaces the Drain Pump (PS11770107). Explains why the pump could be it.
PASS IF: DIY checks present AND Drain Pump returned. (Card shows in [UI].)

--- C2: Dishwasher not cleaning (ambiguous -> expect clarifying) ----------------
TYPE: [UI] and [API]
INPUT:  Dishes come out dirty after a cycle
EXPECT: This symptom is ambiguous, so the assistant should ask a focused
        clarifying question (whole load or just one rack? food residue vs film?
        model number?) and give free checks (clean filter, detergent amount,
        clear spray-arm holes). It may also surface Lower Spray Arm (PS11722150)
        or Heating Element (PS11750673).
PASS IF: EITHER it returns a relevant part, OR it asks a clarifying question
        plus DIY checks. (Both are correct diagnose-first behavior.)

--- C3: Fridge not cooling ------------------------------------------------------
TYPE: [UI] and [API]
INPUT:  My fridge isn't cooling and runs constantly
EXPECT: Free checks (door seal, vents not blocked, temperature setting, coils)
        AND troubleshoot surfaces the Door Gasket Seal (PS12364199).
PASS IF: gasket present; DIY checks mentioned.

--- C4: Vague symptom (relevance stress test) -----------------------------------
TYPE: [UI]
INPUT:  My fridge is broken
EXPECT: Should ASK what's wrong (not cooling? leaking? noisy? ice maker?) rather
        than dumping all five fridge parts. Narrows before recommending.
PASS IF: it asks a clarifying question rather than listing everything.

--- C5: Support offered only as last resort ------------------------------------
TYPE: [UI]
INPUT:  My dishwasher won't drain
THEN:   I tried cleaning the filter and checking the hose, still not draining
EXPECT: First answer leads with self-help, NOT escalation. After the user has
        tried the checks, the assistant can point more firmly to the part and/or
        offer support. Support should never be the FIRST thing offered for a
        repairable symptom.
PASS IF: turn 1 does not lead with "contact support"; self-help comes first.

ONE-LINE SMOKE TEST (paste-and-run sanity check)

Run this to confirm the four core behaviors quickly (backend must be on :8000):

  for q in \
    "How can I install part number PS11752778?" \
    "Is part PS11752778 compatible with my WDT780SAEM1 model?" \
    "The ice maker on my Whirlpool fridge is not working" \
    "How do I fix my oven?"; do
    echo "=== $q ==="
    curl -s -X POST http://localhost:8000/chat -H "Content-Type: application/json" \
      -d "{\"messages\":[{\"role\":\"user\",\"content\":\"$q\"}]}" \
      | python3 -c "import sys,json; d=json.load(sys.stdin); print('tools:', [t['tool'] for t in d['tool_calls']]); print(d['content'][:200])"
    echo
  done

EXPECT, in order:
  1. tools: ['get_installation_guide', ...]   install steps
  2. tools: ['check_compatibility', ...]      NOT compatible (fridge vs dishwasher)
  3. tools: ['troubleshoot']                  ice maker assembly + water inlet valve
  4. tools: []                                polite decline (out of scope)
